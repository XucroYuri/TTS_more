核心流程现为：精确保存原文 → 大模型语义分析 → 原文彩色标注与自由框选修订 → 右侧角色/情感/台词核对 → 允许部分成功 → 人工确认 → 仅将已接受且已分配角色的台词投影到 TTS 工作台。

## 数据完整性与并发自审

审查过程中发现并修复了以下高风险路径：

1. 旧的全项目 autosave 可能覆盖新 ScriptRevision 或已确认语义结果。现通过权威修订合并、epoch、排空屏障和失败重排队保护。
2. 创建 ScriptRevision、ParseRevision、激活修订和角色修改曾存在 `load → mutate → save` 竞态。现统一进入项目级原子更新。
3. 公共 `PUT /api/projects/{id}` 曾只比较修订 ID。现精确比较不可变 ScriptRevision、非活动 ParseRevision 和活动 ParseRevision 的不可变字段，冲突返回 409。
4. 模型调用期间并发产生的新 ScriptRevision 曾可能在 parse 提交时丢失。现模型调用保持无锁，最终提交在项目锁内重新加载最新项目并追加。
5. Windows 上语义 run/draft/index 的读与原子 replace 曾发生共享冲突。所有可变 sidecar 读取现与写入共享项目锁，索引读取共享索引锁。
6. 保存失败、409 或网络中断曾允许项目切换并丢失待保存编辑。现返回明确的 `saved / stale / failed` 结果；失败时保留 pending，恢复权威后才允许切换。
7. 晚到的分析、确认、文件读取或旧解析结果曾可能应用到另一项目。现所有异步操作绑定项目、源修订和 operation token。

锁顺序审查未发现循环：语义公共读取先完成索引查找并释放索引锁，再获取项目锁；写入路径维持项目锁到索引锁的顺序。

## 已知边界

- 未使用用户真实剧本调用外部模型，也未在自动化中读取真实 API 密钥。人工验收时才会验证实际供应商质量与延迟。
- 分析质量受所选模型影响，但错误输出只能形成警告、冲突或部分草稿，不能绕过精确源区间与人工确认门。
- 当前持久化并发保护针对单机进程及同一数据根；跨主机协同编辑不是本规格范围。
- 旧“提取台词”入口继续保留兼容；推荐主流程是新的“分析剧本”工作台。

## 最终裁定

自审通过，可重启本地服务并交给用户使用原剧本进行人工测试。若真实供应商输出不稳定，应首先查看 UI 中持续显示的 trace/error 和 `data/logs/parse-attempts.jsonl` 的安全元数据，再调整模型 Prompt 或供应商配置；不得放宽原文逐字匹配与确认门。
