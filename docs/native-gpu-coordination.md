# 原生 TTS 与 ComfyUI 的 GPU 协调

本机生产使用的原生 TTS 应用需要保持可用。目标是：所有原生 GPU 操作连续五分钟空闲后，把驻留模型和缓存迁移到 CPU；ComfyUI 使用闲时 GPU；原生有新任务时，先让 ComfyUI 收尾并确认释放，再恢复原生 GPU 推理。

## 当前能力边界

现有 GPT-SoVITS 和 IndexTTS WebUI 未提供完整的进程外卸载及恢复接口。部分 GPT-SoVITS 推理类有进程内设备迁移方法，但没有覆盖全部模型和缓存，也未通过 API 暴露。调用 `empty_cache()` 只释放未使用的缓存，不能释放仍被模型持有的显存。

Gradio 的 `queue_size` 仅统计等待事件，不包含正在运行的事件。健康检查、低 GPU 利用率、低 CPU 利用率和空等待队列都不能证明连续五分钟没有任务，也不能保证原生新任务在加载 GPU 前等待 ComfyUI。

服务关闭、进程终止、GPU reset 和对运行中原生进程进行调试注入，不属于本方案。

## 外置启动包装层

包装代码保存在 TTSMore 或 TTS-Audio-Suite 中，使用操作员配置的原生解释器、源码入口和模型路径，不改原生源码或 ComfyUI 核心。首次启用需要在用户安排的维护窗口重新启动对应原生实例；运行中的实例不能安全地临时获得这些能力。

包装层需按受支持的引擎版本实现明确的模型与缓存适配，不能通过任意对象遍历或任意 Python 方法执行接口迁移设备。一个启动器同时提供 WebUI 与 API 时，两个入口及各自持有的模型都必须覆盖。

控制接口只绑定 loopback，使用本机配置的鉴权。机器路径、端口和凭证保存在被 Git 忽略的本机配置中。

## 生命周期与准入契约

原生适配器必须提供活动中 GPU 操作数、等待操作数、活动版本号、距离最近 GPU 操作的单调时钟时长、模型驻留状态，以及进程身份。推理、参考预处理、权重切换和模型加载使用同一把进程内锁；流式生成直到响应结束才归还使用权。

卸载必须是带活动版本号的原子 `offload-if-idle` 操作：活动数和等待数均为零，空闲至少 300 秒，且活动版本未变化，才迁移全部模型与缓存。完成后验证实际分配的 GPU 内存已经下降，再确认可以准入 ComfyUI。失败或状态陈旧时保持关闭准入。

原生新任务先声明优先请求。协调器立即禁止新的 ComfyUI GPU 操作，给当前片段一个有界收尾窗口，必要时定向中断并确认其子进程和模型使用权已释放；随后才允许原生恢复 GPU 模型。协调状态未知时不能允许双方同时加载。

TTSMore 与直接提交到 ComfyUI 的工作流都必须取得同一协调使用权。只在后端排队不能约束绕过工作台直接提交的工作流。局域网独立设备使用独立资源组，不受本机 GPU 忙碌状态影响。

## 被让出的任务

原生优先权引发的中断应与用户取消区分。已完成台词保留，当前未完成台词和后续台词保持等待，闲时自动继续；不能把剩余剧本写成最终取消，也不能重复提交或重复写入音频历史。

ComfyUI 清理确认至少包括：目标 prompt 不再运行、外部子进程树结束、插件活动使用权归零、释放没有错误。释放后清除工作台之前的加载状态，避免后续误认为模型仍驻留。

## 必须完成的验证

- 299.9 秒不卸载；300 秒边界允许卸载；新 GPU 操作重置空闲时间。
- 卸载和恢复过程中原生 PID、创建时间和监听端口保持不变。
- 原生新请求先等待 ComfyUI 完成清理，再加载 GPU；并发请求、权重切换及流式输出都不能绕过门控。
- 每种受支持原生入口分别验证全部模型及缓存的 CPU 迁移、显存下降、GPU 恢复和真实语音生成。
- 直接 ComfyUI 工作流受相同限制，LAN 独立资源组可继续生成。
- 状态超时、活动版本变化、迁移失败或清理失败均关闭准入，原生生产服务保持运行。
- 暂停后继续的剧本只生成一次未完成片段，保留原有完成记录和用户取消语义。

在包装层部署和上述实测完成前，不能将保守的 ComfyUI 停派保护描述为完整自动 GPU 协调。

## 已实现的可选开发接口

`backend/app/native_gpu/` 提供不依赖 FastAPI 的回环鉴权协议、原生优先协调器、持久 GPU 使用记录、进程内活动守卫和明确的设备适配器。原生 Python 可以用独立包名加载它，避免与原生 `app.py` 冲突。普通启动不启用该功能。

`scripts/run-native-gpu-wrapper.py --config <private.json>` 默认只验证配置、源码哈希和路径，不导入模型、不监听端口。只有显式 `--launch` 才运行原生源码。`scripts/run-gpu-coordinator.py --config <private.json>` 同样默认只检查，只有 `--serve` 才启动协调控制服务。

原生配置需要 `kind`、`participant`、原 `python_executable`、`working_directory`、`entry`、`argv`、原启动环境、`source_sha256`、coordinator 和 control 的私有回环地址及 token。启动时仍需使用原解释器及原解释器参数；配置中的 `interpreter_flags` 可保留维护启动依据。支持 `gpt_webui`、同时包含 UI/API 的 `gpt_dual` 和 `index_v2`。GPT Windows 启动补丁必须在导入原生依赖前应用，可配置 `startup_patch=gpt_windows_bootstrap` 并固定其源码哈希。

设备适配当前支持常规 PyTorch GPT v1/v2/v2Pro/v2ProPlus 布局，以及已核实的新版 IndexTTS2 布局。未知版本、其他 GPU、编译/DeepSpeed/Flash 加速、Qwen 量化或分片/磁盘卸载会拒绝迁移。旧 Index 资源项目可继续由 Suite 使用，不能据此推断它也支持原生包装。部署时必须由真实对象检查确认布局，源码检查通过不等于 GPU 迁移验证通过。

Gradio 的同原生命名空间事件共用活动锁；生成器直到消费结束或关闭才归还优先权。GPT API 的推理、参考预处理及两类权重切换覆盖整个 ASGI 请求/流式响应。包装部署后的原生 API `/control` 返回 409，因为其原始 restart 会重新执行未包装入口；服务生命周期通过安排好的维护启动器操作。

Suite 的 unified 文本和 SRT 目标 TTS 节点在模型构造前取得实际 GPU 使用权，心跳撤销后协作终止外部推理，并在返回前清理 runtime、子进程和进程内 CUDA 分配。后端仅进行提交前准入检查，不重复持有节点的使用权。让出 GPU 使用独立的 `SynthesisPreempted`，不追加失败/取消历史，只在重新准入后继续当前尚未提交的台词。用户取消保持原有语义。

此门控覆盖 Suite 支持的 TTS 节点；其他未经门控的 GPU 插件不在保护范围。启用协调的 ComfyUI 实例需只运行受保护的 TTS 工作流，不能混入其他 GPU 节点后宣称整个实例受协调。

## 本机配置和维护部署

所有实际路径、原启动参数、源码哈希、凭证和状态文件存放在 Git 忽略的本机目录中。协调器模板见 `deployment/examples/gpu-coordinator.example.json`，复制后必须换成私有随机 token。coordinator 的 `groups`、后端服务 `resource_group` 和 Suite 的 `resource_group` 必须一致。

后端通过 `TTS_MORE_GPU_COORDINATION_CONFIG` 读取 `{enabled, groups: {<group>: {coordinator_url, token}}}`。Suite 通过 `TTS_AUDIO_SUITE_GPU_COORDINATION_CONFIG` 读取相同 groups，再增加顶层 `resource_group`。配置缺失或 enabled=false 时保持现有流程；启用但无可信状态、能力未对齐或凭证无效时拒绝生成。

协调器必须配置 `journal_path`。批准 Comfy 使用前写入 dirty，只有已知使用权的完整 clean 归还才写回 clean。token 只保存哈希。重启、过期或未知旧 token 不能清除 dirty；日志损坏、丢失、写入失败及控制器锁冲突均需要维护恢复。没有网络 reset/ack-clean 动作。恢复前须由操作员核实旧工作流和所有推理子进程已结束，不能手动删除文件来掩盖尚未释放的 GPU。

首次启用需安排维护窗口，先确认原生没有等待/运行任务，保存原启动方式和端口；仅此时重启为包装入口。初始状态记录必须确认不存在旧的协同 GPU 活动。先验证每个原生入口卸载/恢复时 PID 与端口不变、显存实际下降及真实合成，再启用后端和 Suite 协调；原启动方式保留用于回退。离线测试和配置检查不代替这一生产验证。
